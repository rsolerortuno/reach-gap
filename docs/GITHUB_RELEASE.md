# Publishing reach-gap v0.8.0 on GitHub

The repository is designed so that the source tree and the downloadable release assets remain separate.

## Repository contents

Commit the complete repository tree, including `.github/`, `src/`, `tests/`, `results/`, `reports/`, `docs/`, `scripts/` and the root documentation files. Do not commit built wheels, source distributions or `SHA256SUMS`; those are generated by GitHub Actions.

## Recommended first publication

```bash
git init
git add .
git commit -m "Publish reach-gap v0.8.0"
git branch -M main
git remote add origin https://github.com/rsolerortuno/reach-gap.git
git push -u origin main
```

Wait for the `CI` workflow to pass. Then publish the versioned tag:

```bash
git tag -a v0.8.0 -m "reach-gap v0.8.0"
git push origin v0.8.0
```

The `Publish GitHub release` workflow repeats linting, typing, tests, scientific invariant checks, figure regeneration, packaging and wheel smoke tests before it creates the release. It attaches the wheel, source distribution, checksums, validation JSON files, benchmark output and release reports.

## Manual fallback

The release workflow can also be launched from **Actions → Publish GitHub release → Run workflow**. Supply an existing tag such as `v0.8.0`. The workflow refuses to publish when the tag and `pyproject.toml` version differ.

## Repository settings

Recommended settings:

- public visibility;
- default branch `main`;
- require the CI jobs before merging pull requests;
- enable Dependabot alerts;
- enable private vulnerability reporting;
- use squash merging for small focused changes.
